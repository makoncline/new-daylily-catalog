# Member MCP: primary-source notes

Date: 2026-09-24. These notes check the ideas in [Rhys Sullivan's post](https://x.com/rhyssullivan/status/2103280866084708510) against current primary sources. A direct web fetch of X returned HTTP 403. The main review opened and read the full post in the in-app browser; these notes use its themes and do not quote its text.

## Product actions and human completion

- MCP tools can call APIs and change external systems. The protocol does not require a read-only server. Its [tools specification](https://modelcontextprotocol.io/specification/2026-07-28/server/tools) asks clients to keep a human able to deny tool calls and to show confirmation for operations. This supports adding member actions when the product can enforce ownership and permissions. It does not imply that every dashboard control must become a direct write tool.
- A member dashboard URL returned by a tool can take a person to the exact record, chart, or delete confirmation screen. Treat a normal HTTPS product URL in `structuredContent` and the text response as the portable base. MCP `resource_link` is for a URI that the client can fetch or subscribe to as an MCP resource; it is **not** a guarantee that the host will open a web page. See [tool result types](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#resource-links) and [resource URI guidance](https://modelcontextprotocol.io/specification/2026-07-28/server/resources#common-uri-schemes). If a rich MCP App is later justified, its [openLink API](https://apps.extensions.modelcontextprotocol.io/api/classes/app.App.html#openlink) asks the host to open an HTTPS URL, but the host may deny it.
- For a destructive action, return a URL that opens the authenticated dashboard at a **review/confirmation state**, not a URL that deletes on GET. Bind the target to the signed-in member on the server. A tool may return an operation ID and a status tool can later reconcile whether the user completed the action. This is a product design recommendation, not an MCP requirement. It follows the [elicitation spec's explicit distinction](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation#url-mode-elicitation-requests): the user's acceptance of a URL interaction does not prove that the out-of-band operation finished.
- URL mode elicitation can support a secure browser handoff **only where the client declares URL-mode support**. The spec requires user consent, a displayed destination, and server verification of the person who opens the URL; the link must not contain personal data or act as a pre-authenticated capability. It is primarily for out-of-band sensitive interactions. A regular product deep link in a tool result is simpler and reaches more clients for ordinary navigation. See [capabilities and security rules](https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation).

## Discoverability and data presentation

- Current MCP provides `tools/list` with pagination and caching. The tool set may vary by the bearer token's granted authorization but not by per-connection hidden state or side effects of other requests. The protocol does **not** prescribe a server-side code-mode or lazy-loading meta-tool. See [tools/list rules](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#capabilities). Keep a small, stable set of clear product tools; let capable clients manage their tool context.
- A `search_docs` tool can expose concise member help, workflows, and field definitions. MCP also has [resources and resource templates](https://modelcontextprotocol.io/specification/2026-07-28/server/resources) for read-only reference material. Sentry's [first-party MCP core README](https://github.com/getsentry/sentry-mcp/blob/main/packages/mcp-core/README.md) describes `search_docs` and `get_doc` behind its discovery catalog. This is evidence that searchable docs help a working MCP, not evidence that Daylily needs Sentry's catalog wrapper.
- For search, inventory, and metrics, provide a schema-checked `structuredContent` result with bounded rows and a canonical HTTPS dashboard URL for follow-up. MCP [output schemas and structured results](https://modelcontextprotocol.io/specification/2026-07-28/server/tools#structured-content) support machine-readable data; the same source recommends a serialized text block for older clients. A product link opens the full dashboard view without building a separate visualization system into MCP.

## OAuth and tool groups

- The current [MCP authorization specification](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization) requires protected-resource metadata and authorization-server discovery for remote MCP. The server must accept only access tokens issued for its intended audience. `WWW-Authenticate` can state the scopes for the current operation and let the client request more rights as needed. Read, edit, and destructive scopes are a useful design direction, but their exact names and product policy are application choices.
- [Client ID Metadata Documents](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/client-registration) let an unfamiliar client identify itself by a stable HTTPS metadata URL. The authorization server must advertise support, fetch and validate the document, and check redirect URIs. The spec still permits pre-registration; Dynamic Client Registration remains as a deprecated fallback. CIMD is the strongest current path toward broad client access, but it is **not** enough by itself to make every OAuth client work. The client and server still need compatible discovery, redirect handling, PKCE, token validation, and requested scopes.
- The server may expose only tools allowed by a request's token. Sentry's [first-party security design](https://github.com/getsentry/sentry-mcp/blob/main/docs/security.md) narrows tool exposure by granted skills and optional organization/project constraints, while the upstream Sentry token stays server-held. Its [core README](https://github.com/getsentry/sentry-mcp/blob/main/packages/mcp-core/README.md) documents `inspect`, `triage`, and project-management groups. This supports offering member read and edit groups, with destructive capability gated separately. It does not replace resource-level authorization inside each tool.
- PostHog's [Codex setup guide](https://posthog.com/docs/model-context-protocol/codex) shows a remote HTTPS MCP endpoint with native OAuth sign-in. Its [data-quality MCP reference](https://posthog.com/docs/data-warehouse/data-quality/mcp) distinguishes viewer reads from editor writes and shows an idempotent create operation. These are useful examples for member permission and retry design. They do not establish that PostHog's exact scope scheme fits Daylily.
- If an MCP server calls another service, do not pass the incoming MCP client token downstream. The [authorization spec](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization#access-token-privilege-restriction) requires audience binding; the [security guide](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices#token-passthrough) calls token passthrough an anti-pattern.

## Caveat about an API specification

An OpenAPI document can let an agent with an HTTP-capable harness discover the product API. It is not an MCP server and does not supply MCP tool discovery, resource delivery, host-facing confirmation, or client interoperability on its own. The post's "API spec plus CIMD" idea is a practical alternative channel to test, not a conclusion in the MCP specification. Keep the API and MCP backed by the same member authorization and business operations if both channels are offered.
