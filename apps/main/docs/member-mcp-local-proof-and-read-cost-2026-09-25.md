# Member MCP local proof and read cost

Date: 2026-09-25

## Decision

The member MCP does not need catalog totals. It now exposes current, paged records and exact details, with no aggregate count queries on the member primary. It uses an indexed `LIMIT 1` membership check to decide whether a list can open a deletion confirmation. The public seller profile still uses the local public replica and can include public catalog counts; those calls do not make per-request reads from the Turso primary when the replica is configured.

Turso's [Usage and Billing documentation](https://docs.turso.tech/help/usage-and-billing) says an aggregate function scans every row it considers. An index can limit the scan to one member's rows, but `COUNT(*) WHERE userId = ?` still examines every row for that member. On the local seed, Rolling Oaks has 3,079 listings. The removed overview query would have examined all of them on every call, plus indexed image lookups. A maintained tally would add writes and schema work. No current member MCP task needs that tradeoff. If a real task later needs a total, start with a clearly labelled local replica snapshot.

## Page query plan

The earlier no-schema listing page used `(userId, slug)` and an `s:` cursor. A member can edit a slug between pages, so that cursor can repeat or skip a listing. The current page uses immutable listing ID order and an `i:` cursor. The existing owner-only index made the first ID-ordered page sort all 3,079 listings for the largest seeded owner. The new `(userId, id)` index supplies both the owner filter and ID order. The migration drops the redundant owner-only index because the new index has `userId` as its left prefix. List-filtered listing pages keep their relation ID cursor and use `_ListToListing` first. On the regenerated seed and a migrated disposable copy, `EXPLAIN QUERY PLAN` gave these plans:

```text
SEARCH Listing USING COVERING INDEX Listing_userId_id_idx (userId=? AND id>?)
SEARCH Listing USING INDEX sqlite_autoindex_Listing_1 (id=?)  [list-filtered hydration]
SEARCH List USING INDEX List_userId_idx (userId=?)
SEARCH Image USING INDEX Image_listingId_idx (listingId=?)
SEARCH _ListToListing USING COVERING INDEX _ListToListing_AB_unique (A=?)
```

The list and image page queries pin the existing target indexes with `INDEXED BY`. They sort only that owner or target's rows, then return at most 100. The seed has at most 19 lists per owner, eight images per listing, and five images per profile. The first general listing page needs no temporary sort. A future member with many thousands of lists, or one target with many old images, could make those local sorts costly; that requires a measured workload before adding an index. The list-deletion membership check reads at most one matching relation row because it has `LIMIT 1`. These plans prove local source selection, not billed Turso rows.

The public seller-list summary had a separate full-relation aggregate: Prisma ordered one seller's lists by member count with a `GROUP BY` over `_ListToListing`. It still ran on the local public source, but the work grew with every seller's memberships. The revised query first selects the requested seller's lists with `List_userId_idx`, then counts each selected list's relations through `_ListToListing_AB_unique`. `EXPLAIN QUERY PLAN` shows owner-index selection and correlated relation-index lookups; it shows no global relation scan. The published-listing count and original list order match the prior Prisma query on the realistic seed. Public profile JSON, public list MCP, and list-filtered public listing JSON/MCP parity pass in the opt-in SQLite integration. This needs no schema change. These are local plan and semantic proofs, not a remote cost measurement.

Seller-filtered public listing search previously loaded every paid seller ID before applying one `sellerSlug`. It now resolves that seller on the supplied local public database and checks only that user's subscription cache. The realistic SQLite MCP proof records a `User.id IN (?)` subscription lookup and no all-paid-users lookup for seller search. It also keeps the injected-database, canceled-membership, JSON/MCP parity, and remote-only-source checks green. An unfiltered cross-seller search still loads the active seller set. No new index or schema field is needed.

The dashboard's approved image removal previously selected every remaining image and issued one image and one ImageAsset update per row. It now deletes the owned image, materializes order ranks for that target, updates image order in one SQL statement, and synchronizes linked ImageAsset order in one more statement. There is no post-delete image SELECT or per-image update call.
