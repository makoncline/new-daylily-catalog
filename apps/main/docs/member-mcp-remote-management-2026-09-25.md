## Scope

The remote MCP endpoint is `/api/mcp/server`. It accepts OAuth bearer tokens and works without a browser. Dashboard WebMCP is a separate browser feature. The remote endpoint now advertises 26 tools: nine public/help reads, eight private member reads and handoffs, and nine member write tools.

Private reads and `open_dashboard` require the `catalog:read` OAuth scope. Writes require `catalog:write`, a token issued to the configured Daylily MCP OAuth client, a matching local user, and a confirmed active or trialing membership. The existing dashboard procedures enforce record ownership again. The service checks membership before it starts a write. Public catalog reads use the local replica or search index boundary; they do not fall through to remote Turso when those local sources are absent.

## API boundary and future clients

The server API is the source of the product rules. Its tRPC root already separates `public` and `dashboardDb`. The web dashboard calls `dashboardDb`; remote MCP calls those same protected member procedures for writes. They enforce membership and record ownership on the server. Public pages and public MCP use public read models backed by the local replica or search index. A future admin API belongs behind a separate authorization boundary; it is outside this work.

This separation must hold when the public site and dashboard become separate apps or when an iOS, Android, or CLI client is added. Each client should use the same public read models and member commands, with its own supported login transport. A client-side form or MCP tool must not become the only place that validates a member command. MCP presents product tasks; it does not define an independent set of mutation rules. A separate OAuth client with `catalog:manage` can call destructive member commands after its own user review. The current MCP OAuth client can only use safe commands and dashboard review links.

The web dashboard uses `/api/trpc` with Clerk session tokens. The versioned `/api/v1/member/<procedure>` transport accepts verified Clerk OAuth bearer tokens from a client that Clerk granted the required custom catalog scope. The MCP endpoint separately requires its configured OAuth client ID. The member route exposes only its allowlisted procedures. A read needs `catalog:read`. A safe write needs `catalog:write`. A managed write needs `catalog:manage` and a different OAuth client ID from the MCP app. Every write needs a confirmed active or trialing membership, and the shared procedure enforces record ownership. The transport rejects batching, bounds streamed mutation bodies, sends `Cache-Control: no-store`, and advertises the absolute OAuth resource metadata URL when it rejects a bearer token. The member route allows cross-origin browser calls with an explicit Authorization header and answers their preflight requests. It does not accept a cookie-only member request or send `Access-Control-Allow-Credentials`, so browser session cookies cannot authorize this bearer API. Public tRPC and `/api/v1/cultivars/*` serve public clients. Filtered public listing search now uses one application service from public tRPC `searchListings` and both public MCP listing-search tools.
